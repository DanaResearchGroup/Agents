Build Step 1 of Lane 1: paper discovery and access triage for literature-model evaluation.

Goal:
Create a Python module that searches for relevant literature papers, checks whether they are open access, records whether supplementary information or mechanism files may be available, and saves all candidate papers into structured files for downstream use. This step is only for discovery and triage. Do not run simulations yet.

Context:
We are building Lane 1 of a two-lane workflow. Lane 1 is only for independent literature model evaluation. We want to identify relevant references, determine whether they are accessible automatically, and tag non-OA papers that are still worth manual download using a campus account.

What this step should do:
1. Search for candidate papers relevant to a user query or discrepancy topic.
2. Retrieve metadata for each paper, such as title, authors, year, journal, DOI, abstract if available, and publisher/source link.
3. Check whether each paper is open access.
4. Try to find possible supplementary information links, repository links, or hints that mechanism files may exist.
5. Score and tag each paper for likely usefulness.
6. Save all results to structured files, including a separate queue for high-interest non-OA papers that require manual retrieval.
7. Do not attempt institutional login automation.
8. Do not download paywalled PDFs through browser automation or campus SSO.
9. Be robust, auditable, and easy to extend later.

Preferred external sources/APIs:
- Crossref for metadata lookup
- Unpaywall for OA status and OA locations
- OpenAlex and/or Europe PMC if useful for metadata enrichment or OA/full-text signals
- If a source is unavailable, fail gracefully and continue

Inputs:
The module should accept either:
- a free-text topic query, such as "HOCHO pyrolysis mechanism CO underprediction"
or
- a structured search object like:
  {
    "topic": "HOCHO pyrolysis",
    "keywords": ["formic acid", "pyrolysis", "mechanism", "kinetics", "CO"],
    "year_min": 2000,
    "max_results": 30
  }

Outputs:
Produce at least these files:

1. paper_registry.yaml
Contains all candidate papers, including OA and non-OA papers.

2. manual_retrieval_queue.yaml
Contains only high-interest non-OA papers that should be downloaded manually later.

3. optional: paper_registry.json
Same content as the YAML registry for easier machine use.

Required output schema for each paper in paper_registry.yaml:
- id: stable internal identifier
- title: string
- authors: list of strings
- year: integer or null
- journal: string or null
- doi: string or null
- abstract: string or null
- source_url: string or null
- oa_status: one of ["oa", "non_oa", "unknown"]
- oa_url: string or null
- relevance_score: float between 0 and 1
- priority: one of ["high", "medium", "low"]
- tags: list of strings
- relevance_reason: list of short strings
- si_link_found: boolean
- si_links: list of strings
- mechanism_link_found: boolean
- mechanism_links: list of strings
- access_notes: string or null
- manual_review_needed: boolean
- keep_for_manual_review: boolean

Required schema for manual_retrieval_queue.yaml:
manual_retrieval_queue:
  - id: ...
    title: ...
    doi: ...
    year: ...
    journal: ...
    priority: ...
    reason: ...
    source_url: ...

Tagging rules:
Use tags such as:
- oa
- non_oa
- unknown_access
- high_interest
- medium_interest
- low_interest
- possible_si
- possible_chemkin
- possible_cantera
- possible_mechanism
- kinetics_relevant
- mechanism_comparison
- pressure_dependent
- manual_review_needed
- conditions_relevant

Scoring guidance:
Compute a relevance score using simple transparent heuristics. For example:
- title contains target species or fuel
- abstract contains "mechanism", "kinetics", "model", "supplementary", "Chemkin", "Cantera", "sensitivity", "flux"
- paper appears to discuss experiments plus simulations
- paper likely contains reusable model information
Do not use opaque scoring. Keep the scoring logic explicit in code.

Priority guidance:
- high: strongly relevant and likely useful for Lane 1, especially if it likely contains mechanism/SI
- medium: relevant but uncertain whether usable assets exist
- low: weakly related or unlikely to contain reusable model assets

Behavior rules:
- Search and collect candidate papers first
- Deduplicate by DOI when possible, otherwise by normalized title
- Enrich metadata from multiple sources when helpful
- Never assume non-OA means unimportant
- Non-OA but relevant papers should still be kept and possibly added to manual_retrieval_queue.yaml
- If OA full text or SI links are found, record them
- If only metadata is found, still keep the paper if relevance is high enough
- Do not attempt to parse PDFs yet
- Do not run simulations yet
- Do not convert mechanisms yet

Implementation requirements:
- Use Python
- Organize code cleanly into functions/classes
- Include type hints
- Include logging
- Include error handling and retries where reasonable
- Keep source-specific logic modular so more providers can be added later
- Save outputs deterministically
- Make the code runnable from CLI

Suggested CLI:

Expected pipeline:
1. take user query
2. search candidate papers from metadata providers
3. normalize and deduplicate records
4. enrich records with OA/access information
5. inspect available metadata/links for SI or mechanism hints
6. compute relevance_score and priority
7. assign tags and reasons
8. write paper_registry.yaml
9. write manual_retrieval_queue.yaml

Important constraints:
- Do not automate campus login
- Do not use browser automation for paywalled downloads
- This step is triage only
- The code must make it easy for a human to manually continue later

Deliverables:
1. working Python code
2. YAML outputs matching the schema above
3. clear README-style usage notes
4. one small example run with mock or real metadata results

Design philosophy:
This module should function as the "paper triage and retrieval planning" step of Lane 1. It should help us answer:
- Which papers are relevant?
- Which are open access?
- Which may contain SI or mechanism files?
- Which non-OA papers are important enough for manual retrieval?

Please implement the MVP first, favoring clarity and reliability over complexity.
